# Продуктовый аудит BJJ Companion (2026-07-26)

Роль: `bjj-product-reviewer`. Оценка ФАКТА по коду, не идеала. Это НЕ пересказ аудита
2026-07-22 и разбора опроса — они прочитаны, здесь развитие с учётом всего, что построено
после (сессии 25-29: пивот по видео, крючок после тренировки, вечерний пинг, партнёры +
холодный старт, XP/уровни, избранное, инлайн-словарь, ролевые позиции, «Что если»).
База: 336 техник (была 335; +карточка защиты седла 2026-07-26).

## Резюме (что изменилось с 22 июля)

За четыре сессии на ядро надстроили внушительный слой удержания: пост-тренировочный крючок
(«Разбери показанное»), вечерний soft-пинг бота, партнёры по залу с холодным стартом, XP/уровни,
избранное, тап-активный словарь. Петля-ядро осталась здоровой, дизайн-система единая. Но сместился
центр тяжести проблемы. Раньше слабость была «монетизация не построена + вирусность недокручена».
Сейчас острее другое: **построена почти вся машинерия удержания, но её payoff пуст, а результат не
измеряется**.

Три вещи, которые выпирают из кода:
1. **Видео-инфраструктура полностью готова, а видео — ноль.** `data/video-urls.json` = `{}`,
   `videoUrl` нет ни у одной из 336 техник. На КАЖДОЙ карточке без видео (то есть на всех) рендерится
   `VideoInterestPrompt` с текстом «Видео-разбора пока нет». №1 запрос опроса стал негативным
   сообщением на всех карточках без единого исполнения.
2. **Пост-тренировочный крючок — стратегическая ставка сессий 25-27 — упирается в этот же пробел.**
   Вечерний пинг → запись дневника → блок «Разбери показанное» → открыть карточку. Но карточка,
   которую открывают «чтобы разобрать показанное», говорит «видео пока нет». Мост «понимание→тело»
   (главная возможность из опроса) обрывается ровно в точке максимального намерения.
3. **Много нового построено на интуиции и не измеряется.** События пишутся (21 в белом списке), но
   read-запросы в SQL покрывают только исходные 10; нет кривой удержания (D1/D7/D30) и воронок для
   партнёров/разбора/уровней. При этом онбординг спереди стал ДЛИННЕЕ (гейт согласия + тизер добавили
   ~2 экрана до 7 шагов).

Вывод: следующий крупный шаг — не строить ещё одну систему, а **наполнить и измерить уже построенное**.
Самая дешёвая и самая высокая по влиянию точка — курированные видео-ссылки (решение о них уже принято
в сессии 26.C, но файл пуст).

## Топ-5 приоритетов (ранжировано по влиянию на удержание при малой базе)

### 1. Наполнить `video-urls.json` курированными ссылками — S, наивысший ROI
- **Проблема (код):** `data/video-urls.json` = `{}`; 0 из 336 техник имеют `videoUrl`;
  `VideoInterestPrompt` показывает «Видео-разбора пока нет» на всех карточках. Это хуже отсутствия
  фичи: приложение активно сообщает про отсутствие того, что аудитория просит громче всего (опрос,
  блок 1). И это ломает payoff уже построенного крючка после тренировки (п.3).
- **Изменение:** засеять 20-40 бесплатных YouTube-ссылок под самые нужные техники (фундамент по поясу
  + то, что реально показывают в зале). Приоритет брать из уже существующего read-запроса
  `pro_video_interest by detail` (docs/sql/2026-07-22-video-interest-telemetry.sql) — если данных мало,
  начать с фундаментала белого/синего. Пайплайн готов: `video-urls.json → build-data → videoUrl →
  VideoBlock`. Формат уже эмбед YouTube.
- **Эффект:** закрывает №1 запрос; наполняет payoff крючка «разбери показанное» (открыл карточку —
  увидел, как делать); превращает `VideoInterestPrompt` из «извинения» в реальный сигнал спроса на то,
  чего ещё нет. Прямое влияние на «зачем открывать после тренировки».
- **Согласованность:** это ровно решение сессии 26.C (курированные бесплатные ссылки), просто не
  исполнено. НЕ противоречит «не продавать видео» — ссылки бесплатны, ценность в курировании под базу.

### 2. Retention-линза + воронки новых поверхностей — S
- **Проблема (код):** read-запросы есть только для исходных 10 событий (2026-07-18-telemetry.sql).
  Для review_opened / invite_created→invite_accepted / partner_opened / level_up / pro_video_interest /
  glossary_open готовых разрезов нет (кроме одного видео-запроса). Нет когорт D1/D7/D30 и кривой
  возврата. За 4 сессии построены партнёры, XP, крючки — и нет ответа, работает ли хоть что-то.
- **Изменение:** добавить в docs/sql набор запросов (таблица bjj_events уже пишется, менять код не
  надо): (а) retention по когортам первого app_open; (б) воронка партнёров invite_created→
  invite_accepted→partner_opened; (в) воронка крючка entry_saved→review_opened→review_drill;
  (г) распределение level_up; (д) pro_video_interest / glossary_open по detail = что курировать.
- **Эффект:** решения (видео-очередь, судьба трёх реко-блоков, судьба XP, монетизация) на данных, а не
  на глаз. Разблокирует все отложенные «по телеметрии» пункты.
- **Прим.:** это единственный чисто-аналитический шаг; без него следующие ставки — угадывание.

### 3. Срезать трение холодного старта — M
- **Проблема (код):** путь до ценности вырос: ConsentGate (тизер-слайд → экран согласия) → Onboarding
  (7 шагов: welcome-слайдер, пояс, Gi/No-Gi, цель, частота, знакомые техники, финал) → приложение.
  ~10 экранов. Опрос: часть теряется («не сразу понимаю, что можно делать»). Из 7 шагов реальную
  ценность несёт шаг 5 (знакомые техники → засев progress → непустой старт); `goal` (шаг 3) почти не
  влияет (см. п.4); welcome-слайдер и финал — церемония.
- **Изменение:** (а) объединить/сжать: welcome-слайдер уже дублирует тизер ConsentGate — один из двух
  убрать; финальный экран-сводку схлопнуть в тост. (б) Сделать шаг «знакомые техники» героем (он
  единственный чинит пустой старт), остальное — минимум. Цель: 7 шагов → 4-5.
- **Эффект:** выше завершение онбординга и D1. Активация — узкое место воронки при малой базе.
- **Осторожно:** решение пользователя «онбординг не резать» (сессия 23) касалось СОДЕРЖАНИЯ ценности;
  здесь речь о дублях церемонии, не о вырезании смысла. Согласовать явно.

### 4. `goal` — включить в генератор или убрать из онбординга — S-M
- **Проблема (код):** `goal` собирается на шаге 3, влияет ТОЛЬКО на мягкий бонус сортировки в
  `nextToLearn` (recommend.ts::goalScore). В `generateWorkout`/`generateWorkoutFromDiary` (workout.ts)
  goal не участвует вообще — «Отработка» под цель не подстраивается. Пользователь платит шагом
  онбординга за фичу, которой почти нет. (Диагноз повторяет 22.07 — за 4 сессии не тронут.)
- **Изменение:** либо (а) прокинуть goal в `availableFor`/score генератора (self-defense → escape/
  takedown/fundamental вверх; competition → points_ibjjf>0 & легально по формату, adcc); либо (б)
  убрать шаг 3 из онбординга (см. п.3) и оставить goal необязательной настройкой в листе игрока.
- **Эффект:** либо цель реально ощущается в главном действии, либо онбординг короче. Оба исхода
  лучше текущего «собрали и не используем».

### 5. Первый партнёр + сдержанность к XP — M
- **Проблема (код):** петля партнёров построена целиком, но при малой базе у большинства 0 партнёров —
  ценность = 0 до первого принятого инвайта (сетевой эффект). Холодный старт есть (momentum-призыв в
  пустом состоянии PartnersBlock при planStreak>=1 / dayStreak>=3), но он за реальным Telegram и
  срабатывает только у тех, кто уже в темпе. Параллельно: XP/уровни — сам пользователь в сессии 29
  заключил «построили раньше смысла, ничего не открывают».
- **Изменение:** (а) вынести призыв «позови партнёра» в более раннюю/заметную точку (после первой
  записи или первой недели в плане, не только в свёрнутом блоке), упростить инвайт до одного тапа-шеринга
  (хелпер `sharePartnerInvite` уже есть). (б) НЕ углублять XP/геймификацию до данных п.2 — если level_up
  мёртв, вариант D из сессии 29 (тихо демотировать LVL-бейдж), а не новые ранги/титулы.
- **Эффект:** партнёрская петля начинает работать (взаимная подотчётность = удержание); не тратим силы
  на слой, который сам пользователь оценил как слабый.

## Уже хорошо — не трогать

- Петля дневник → награда (XP + reward) → стат/стиль → рекомендации: ядро, ради которого продукт
  существует. Форма дневника: 2-тапа запись (техника из группы/поиска + Сохранить), вторичные поля под
  «Подробнее» — трение снижено грамотно.
- Пост-тренировочный крючок как МЕХАНИКА (ReviewShownBlock само-очищается, «разобрал» = открыл карточку,
  «В отработку» → src=diary) — архитектурно правильный, ему нужен только контент (п.1).
- Вечерний soft-пинг: шлёт только в тренировочный день при недоборе и в рамках капа 2/нед — не спам.
- База 336 + производные (ролевые позиции, «Что если» с матрицей, словарь 77, инлайн-подсветка терминов,
  граф) — ров, который дорого копировать.
- Безопасность/приватность гейта согласия: hasConsent() реально гейтит все отправщики; локальный режим.
- Дизайн-система (navy/gold, Inter, общие компоненты), уплотнённый ProgressTop.
